# SEO-архитектура Nabo: 19 октября 2026

## Исправлено

- Единственный canonical origin — `https://nabo.by`, включая canonical, Open Graph/Twitter, JSON-LD и sitemap. Старые/ошибочные deployment variables больше не могут подставить Vercel, www, localhost или dev-домен.
- Основной контент главной, рецептов, подборок, товарных разделов и сравнения выводится сервером. На главной три рецепта доступны в HTML; фотографии подгружаются при видимости, без возврата ранней загрузки тяжёлых фото.
- Расширены title/description и позиционирование: выбор блюда, продукты, наличие, корзина, приготовление или заказ, а не только самая низкая цена.
- Robots разрешает публичные страницы; закрыты API (кроме прокси изображений), admin, auth и техническая ошибка. Личные страницы и поиск с произвольными параметрами имеют noindex; фильтры не размножают SEO-страницы.
- Пустые подборки/товарные разделы получают noindex и исключаются из sitemap. Реальная пагинация сохраняет собственный canonical и crawlable ссылки.
- Неизвестные/удалённые рецепты, продукты и разделы возвращают 404. Сбоев поставщика не выдаём за отсутствие товара: используется 503.
- Короткие адреса существующих категорий перенаправляются в уже имеющийся каталог, а не дублируют его. Пользовательские категории не перехватывают URL рецептов.

## Создано

- `/products/:slug`: конечный словарь из восьми продуктовых разделов — moloko, tvorog, smetana, yaytsa, kurinoe-file, kartofel, muka, maslo-slivochnoe. Показываются реальные варианты из SEO feed, магазин, фасовка, связанные рецепты и ссылки для проверки цен. Доступные свежие цены выводятся для шести вариантов; при недоступности нет фиктивной цены.
- `/recipes/quick`, `/recipes/budget`, `/recipes/high-protein`: реальные подборки по времени/редакционному тегу/КБЖУ. `/recipes/lunch` и `/recipes/dinner` готовы для явно отмеченных редакцией рецептов; пока нет данных, они noindex и отсутствуют в sitemap.
- `/cook-or-order` и `/cook-or-order/:recipe-slug`: самостоятельный сценарий сравнения, связанный с основным рецептом. Ингредиенты, порции, время, полученная стоимость упаковок/порции и предложения Delivio. Цена не включает доставку; неизвестные доставка/ETA не придумываются.
- `SeoBreadcrumbs`, `RecipeTopicPage`, `RecipeConnections`, `shared/seo/topics.ts`, публичные API товарных разделов/сравнения, общие SSR-утилиты цен и рецепта.
- Backend `nabo-recipes`, commit `15fb803`: буквальный case-insensitive префикс `q` в `/api/seo/products` с пагинацией на стороне БД. Нельзя получить весь каталог SQL wildcard-символом `%`; фильтрация не скачивает тысячи записей на фронт.
- Воспроизводимый read-only аудит: `node scripts/audit-seo.mjs`. HTTP/SSR-тест: `npm run test:seo`, дополнительно `node tests/seo-smoke.mjs --browser` для 390/1440 px.

## Индексируемые страницы

Главная; каталоги рецептов и непустые категории/подборки; опубликованные рецепты; каталог товаров; непустые продуктовые разделы; реальные SKU с полноценной страницей; магазины и страницы шести сетей; доставка; каталог и страницы сравнения приготовления с заказом. Произвольные поисковые запросы не создают новые посадочные страницы.

## Noindex

Корзина, сохранённое, аккаунт, админка, промоссылки `/l/`, API, произвольные комбинации поиска/фильтров, некорректная пагинация, пустые подборки, preview-хосты. API изображений остаётся доступным ботам. Запрет robots не применяется ко всему сайту. На preview нет sitemap; бот может прочитать noindex публичного HTML.

## Redirects

В приложении подготовлены 301: `www.nabo.by/*` → `nabo.by/*`, старый точный Vercel alias → `nabo.by/*`, `/stores/euroopt` → `/stores/evroopt`, короткие существующие категории → `/recipes/category/:category`, query-category → каталог категории, trailing slash → путь без slash. Query string сохраняется. Неизвестные страницы не отправляются на главную.

Vercel обрабатывает домены до приложения. Для миграции www → apex предусмотрена защита от цикла: www-редирект включается после успешного HEAD `https://nabo.by/robots.txt`, результат проверки кэшируется на 60 секунд. Владелец подтвердил переключение primary-домена в Vercel. Фактические production-ответы фиксируются отдельным отчётом, не подменяются локальным тестом.

Старый `nabo-new.vercel.app` на момент аудита возвращал platform 404 `DEPLOYMENT_NOT_FOUND`. Код приложения не может выдать 301 для alias, не привязанного к deployment. Если нужен именно 301, alias необходимо восстановить/переназначить в Vercel; после этого сработает подготовленный редирект.

## Sitemap

`/sitemap.xml` — динамический индекс. `static.xml` содержит публичные hubs, магазины, только непустые категории/подборки/продуктовые разделы. `recipes-N.xml`, `cook-or-order-N.xml`, `products-N.xml` разбиты по 2000 записей. Количество частей определяется backend manifest, новые опубликованные рецепты входят автоматически. В SKU feed используются реальные обнаруженные позиции за последние 30 дней. Личные страницы, API, query-фильтры и неканонические URL не включаются. Даты изменений не выдумываются.

## Schema

Organization, WebSite с рабочим SearchAction по рецептам, WebPage, BreadcrumbList, ItemList; Recipe только на собственно рецепте; Product/Offer только для конкретного товара с фактическими сведениями. Recipe содержит реальные ингредиенты, шаги, время, порции, КБЖУ и белорусскую кухню только при соответствующем теге. Рейтинги/отзывы не создаются. Продуктовые категории и сравнение не маскируются под один продаваемый Product. JSON-LD безопасно сериализуется и проверяется JSON.parse в HTTP smoke.

## Данные и производительность

Публичные расчёты подписаны адресом «Минск, центр». Домашний расчёт — Евроопт, целые упаковки, порции исходного рецепта, без базовых ингредиентов из домашнего запаса, если они так отмечены в справочнике. Это стоимость покупки, а не точная себестоимость съеденного продукта. Цены и предложения ресторанов не сравниваются как идентичные порции: размеры, упаковки и доставка различаются.

Используются существующие подбор/расчёт упаковок и парсер Delivio. Опциональные цены не задерживают SSR более 800–1000 мс; фоновые запросы завершаются через event.waitUntil и обновляют кэш. Числа скрываются при неполном подборе/сбое. HTML с персональным аккаунтом не кэшируется публично. Кэш публичных цен не содержит сессию/телефон/пользовательский адрес. Изменений аналитического согласия, дизайна корзины и авторизации нет.

## Нужно сделать вручную

1. Переключение Vercel проверено: apex → 200, www → 301 apex без цикла. Переменная `NUXT_PUBLIC_SITE_URL=https://nabo.by` указана в `.env.example`; код также защищён от старого значения.
2. Google Search Console: Domain property `nabo.by`, DNS-подтверждение, отправить `https://nabo.by/sitemap.xml`, проверить live URL рецепта и сравнения. Для URL-prefix подтверждения предусмотрен `NUXT_PUBLIC_GOOGLE_SITE_VERIFICATION`.
3. Яндекс Вебмастер: подтвердить `https://nabo.by`, проверить зеркало и sitemap. При meta-подтверждении — `NUXT_PUBLIC_YANDEX_VERIFICATION`. Токены не придуманы.
4. При необходимости восстановить старый Vercel alias для 301. Он сейчас не является доступным индексируемым дублем, поскольку отвечает 404.

SSR smoke проверяет HTML с Googlebot, canonical, robots, X-Robots-Tag, JSON-LD, реальные тестовые суммы упаковок/порции, 404, редиректы, пагинацию и sitemap. Дополнительная браузерная проверка трёх новых шаблонов на 390/1440 px: один H1, breadcrumbs, отсутствие JS-ошибок и горизонтального переполнения. Фикстуры изолированы от production.

Буквальная prefix-фильтрация дополнительно проверена read-only на production: «молоко» вернуло 213 позиций вместо общего индекса 1367. Production HTTP/SEO и Lighthouse после публикации фиксируются в `docs/audits/`.

INP — полевая метрика: лабораторный TBT не подменяет INP. Для полевых CWV необходим достаточный объём реальных посещений/данные Search Console. Индексация и позиции зависят от поисковых систем; наличие корректной архитектуры не является обещанием трафика.

## Следующие SEO-задачи

- **P0:** подтвердить ownership в Google/Яндексе; primary-домен и редиректы уже проверены на production; если Vercel alias остаётся отвязанным, приложение не может управлять его ответом.
- **P1:** редакционно проверить категории существующих рецептов (в исходных данных, например, есть выпечка в основных блюдах); явно отметить обеды/ужины, а не автоматически присваивать блюдам неподтверждённый контекст. Следить за удалёнными SKU и актуальностью feed, сверять Rich Results и индексирование.
- **P2:** расширять словарь продуктовых разделов только при наполнении/пользовательской ценности; улучшать фото и вариативность рецептов, анализировать поисковые запросы и полевые CWV, добавлять данные доставки/ETA только после появления надёжного источника.

Основания: [canonical и редиректы](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls), [Recipe structured data](https://developers.google.com/search/docs/appearance/structured-data/recipe).

## Production-подтверждение

`audits/seo-production-2026-10-19.json` содержит реальные ответы после деплоя: публичные шаблоны — 200, canonical/og:url — apex, один H1, JSON-LD без ошибок; поиск — noindex; три отсутствующих URL — 404 и оформленная Nabo-страница с noindex. Googlebot и обычный User-Agent получают один публичный контент. Sitemap: 32 статические посадочные страницы, 42 рецепта, 42 страницы сравнения и 1645 SKU на момент проверки; чужих доменов в loc нет. Число товаров меняется вместе с реальным feed.

Отдельно исправлена обнаруженная HEAD-проблема robots/sitemap, из-за которой не включался защитный редирект с www. GET и HEAD теперь оба поддерживаются. Производственная проверка: `www.nabo.by/recipes/syrniki?utm_source=audit` → 301 `nabo.by/recipes/syrniki?utm_source=audit`.

Lighthouse главной: два мобильных замера 92/100/100/100 и 100/100/100/100. Во втором LCP 1,4 с, CLS 0. Сохранены оба результата; балл не гарантируется для каждой сети/нагрузки. Сравнение: 97/100/100/100, LCP 2,4 с. У рецепта дополнительный замер выявил потерю серверных предложений Delivio при гидратации и недостаточный контраст ссылки. Начальное состояние передано через useState, подписи карточек больше не перекрывают видимый текст, ссылки используют доступный оттенок синего. Добавлена проверка ошибок гидратации при SSR с реальными по структуре предложениями. После этого повторены сборка, SSR/browser smoke и 10 затронутых desktop/mobile сценариев.

При смене www на apex браузерные сессии относятся к разным origin: может понадобиться повторный вход; серверная корзина восстанавливается после авторизации. Гостевое sessionStorage старого origin не переносится автоматически. Это следствие запрошенной миграции домена, а не изменение срока авторизации.
