# SEO Nabo: аудит, архитектура и запуск

Дата аудита: 12–13 октября 2026. Основной адрес: https://nabo-new.vercel.app.

## Что мешало индексации

- Общие title/description почти для всех страниц; отсутствовали canonical и социальные метаданные.
- Не было robots.txt, sitemap index и автоматического перечисления опубликованных URL.
- Товар загружался в `onMounted`: без JavaScript вместо карточки был индикатор загрузки.
- Рецепты были доступны в SSR, но категории и пагинация использовали кнопки. Ошибки API могли выглядеть как обычная страница с HTTP 200.
- Предложения Delivio существовали только в клиентском HTML.
- Каждый запрос рецептов, в том числе одного рецепта, получал полный опубликованный каталог.
- Ритейл API не предоставляет полный фид товаров. Нельзя достоверно перечислить все SKU простым сканированием маршрутов фронта.

## Что реализовано

- Единая политика canonical, robots, title, description, Open Graph/Twitter; JSON-LD безопасно экранируется.
- Recipe: реальные ингредиенты, шаги, порции, время и доступное КБЖУ. Не добавляются выдуманные рейтинги, авторы, даты или стоимость рецепта.
- Product/Offer: публичный серверный запрос по SKU, настоящие цена, наличие и продавец. Регион первичного публичного HTML — Минск, центр; после загрузки интерфейс обновляется под адрес пользователя.
- BreadcrumbList и ItemList для каталогов. Шаги приготовления имеют адресуемые якоря.
- `/recipes/category/{category}` — постоянные адреса категорий. Старые `/recipes?category=...` перенаправляются 301; поиск и комбинации фильтров не индексируются.
- Пагинация имеет обычные ссылки. Страницы `?page=2` не канонизируются на первую страницу. Неизвестные рецепты и товары отдают 404; сбой сервиса не маскируется под исчезновение товара.
- `/delivery` — публичная точка входа для готовых блюд, ведущая к реальным предложениям на странице рецепта. Предложения в исходном HTML и MenuItem/Offer появляются только при успешном ответе Delivio. На ожидание выделено 2,5 секунды, отказ поставщика не блокирует рецепт. Клиент продолжает обычную загрузку предложений.
- `/robots.txt`, `/sitemap.xml`, `/sitemaps/static.xml`, `/sitemaps/recipes-N.xml`, `/sitemaps/products-N.xml`. Каждая часть — максимум 2 000 записей. Ошибка фида отдаёт ошибку сервера, а не ложный пустой sitemap.
- Корзина, сохранённое, аккаунт, админка и служебные подборки исключены через robots meta и X-Robots-Tag. API не индексируется; endpoint изображений разрешён роботам. JavaScript/CSS не блокируются.
- Vercel Preview отключает индексацию. Для прочих тестовых доменов есть явный флаг.
- Постоянный индекс товаров в PostgreSQL `nabo_recipes.seo_products`, уникальный `(store_id,id)`. Никакие основные таблицы Nabo не меняются. Хранятся название, единица, фото и технические даты; координаты, телефон и персональные цены не сохраняются.
- Известные товары автоматически обнаруживаются из успешных ответов поиска, batch search, resolve и карточек. Запись защищена серверным ключом, выполняется в фоне через Nitro `waitUntil`, разбивается на пакеты по 50; не задерживает выдачу результатов поиска. Preview не пишет в индекс.
- В sitemap попадают товары, встречавшиеся за последние 30 дней. Цены в индексе не фиксируются: карточка сверяет их с ритейлом. Для массового импорта известного легитимного фида есть тот же защищённый endpoint, до 200 позиций на запрос.
- Новые серверные endpoints возвращают отдельную запись/страницу/метаданные, а не все документы. SQL-параметры не интерполируются в запросы. Публичные ответы кэшируются на 60 секунд; приватная корзина и HTML с пользовательским состоянием не получают общего CDN-кэша.

## Запуск на Railway и Vercel

1. Обновлённый `nabo-recipes` уже запушен; таблица индекса создаётся при запуске в текущей общей PostgreSQL. Новые endpoints:
   - `GET /api/recipe-catalog/page?q=&category=&collection=&offset=0&limit=24` (до 100 документов);
   - `GET /api/recipe-catalog/{slug}`;
   - `GET /api/seo/manifest`;
   - `GET /api/seo/recipes?offset=0&limit=2000`;
   - `GET /api/seo/products?offset=0&limit=2000&storeId=green`;
   - `POST /api/seo/products`, `{items:[{storeId,id,name,unit,image}]}`, заголовок `X-Nabo-Seo-Key`.
2. Создайте случайный ключ, например `openssl rand -hex 32`. На Railway **сервиса nabo-recipes** задайте `SEO_INGEST_KEY`. На Vercel задайте **тот же ключ** в `NUXT_SEO_INGEST_KEY`. Это приватные переменные, без `PUBLIC`, не помещайте ключ в Git или браузер.
3. На Vercel Production задайте:
   - `NUXT_RECIPES_API_BASE=https://nabo-recipes-production.up.railway.app`;
   - `NUXT_PUBLIC_SITE_URL=https://nabo-new.vercel.app` (при смене домена заменить и сделать 301 со старого домена);
   - `NUXT_PUBLIC_SEO_INDEXABLE=true`.
4. Перезапустите сервис Railway и сделайте redeploy Vercel после изменения переменных. До назначения ключа рецепты и sitemap работают, но **автоматическое наполнение индекса товаров отключено**. После поиска реальные SKU появятся в `/api/seo/products` и product-sitemap. На момент проверки фид содержал 41 рецепт и 0 товаров: это ожидаемо до подключения ключа.
5. Добавьте сайт в Google Search Console и Яндекс Вебмастер, подтвердите владение и отправьте `/sitemap.xml`. Для HTML-подтверждения поддерживаются `NUXT_PUBLIC_GOOGLE_SITE_VERIFICATION` и `NUXT_PUBLIC_YANDEX_VERIFICATION`: только значение выданного сервиса токена.
6. Для Preview/staging используйте `NUXT_PUBLIC_SEO_INDEXABLE=false` и защиту доступа Vercel. Не задавайте `true` общим значением сразу для всех окружений — это переопределит автоматическую защиту Preview.

## Проверки

- `npm run typecheck`, `npm test`, `npm run build`.
- `npm run test:seo` после сборки: поднимает отдельные тестовые API и сервер на 3120/3121, проверяет исходный HTML без JS, схемы, canonical, HTTP 404, noindex, 301, категории, пагинацию, фоновые записи и sitemap на 4 001 рецепте/2 001 товаре. Не использует рабочую БД и не обращается к внешним поставщикам.
- В `nabo-recipes` GitHub Actions собирает .NET 10 и запускает проверки с отдельной PostgreSQL 17. `TEST_DATABASE_URL` допускается только для одноразовой тестовой БД: тесты удаляют тестовую схему!
- После деплоя проверьте View Source у рецепта/товара, ответ robots.txt и XML, затем Rich Results Test/URL Inspection и диагностику Яндекс Вебмастера.

## Ограничения и дальнейшая работа

- Индекс известных товаров не является полным инвентарём ритейла. Для полного покрытия десятков тысяч SKU нужен легитимный товарный фид/экспорт или обход официального каталога со стороны основного бэкенда. Добавление несуществующих SKU ради sitemap не используется.
- Часть магазинов не поддерживает загрузку товара по ID: для них используется сохранённое название и поиск с проверкой того же SKU. До наполнения индекса отдельные чистые URL таких магазинов могут временно возвращать 503.
- Для предложений готовых блюд география и цены зависят от адреса. Не создаются фиктивные страницы заведений без достаточных собственных данных; известные предложения индексируются в контексте блюда.
- Некоторые текущие фото — внешние ссылки/миниатюры. Для устойчивого SEO и крупных изображений в поиске нужны собственные разрешённые изображения высокого разрешения в планируемом R2, стабильные URL и корректная атрибуция. Удалённые сторонние фото Nabo не контролирует.
- Schema.org и sitemap помогают поисковикам понять сайт и обнаружить URL; индексация и расширенные сниппеты не гарантируются. Core Web Vitals и поисковый трафик нужно оценивать на реальных данных Search Console/Метрики после деплоя, а не заявлять как уже пройденные.
- После изменения рецепта публичный кэш обновляется в пределах минуты. Не используются выдуманные `lastmod`: у рецептов поле не выдаётся до отдельного учёта даты изменения опубликованной версии; у товаров оно отражает изменение метаданных.
